Everyone hands the model a database. I built the part that says no

Everyone is busy giving language models access to the company database. Almost every tool that does it works the same way: the model writes some SQL, the server runs it, the rows come back. Connecting to a warehouse is the easy part. It has been easy for forty years.

The hard part is everything wrapped around that. Can you prove this query only reads? Do you know what it costs before you pay for it? Whose permissions is it running as? And when someone asks next month why the payments table got scanned at three in the morning, can you answer?

I wanted to see if I could build that missing layer. It sits between the model and the warehouse and it is allowed to say no.

01The query that taught me the whole problem

Start with the simplest guard anyone writes: does the query start with SELECT? It is one line and it feels reasonable. It is also wrong often enough to be dangerous.

So you get smarter. You parse the SQL properly and look at what kind of statement it is at the top. This feels like the grown up solution. Then you meet this:

WITH d AS (DELETE FROM orders RETURNING *) SELECT * FROM d

That is a SELECT. The parser agrees it is a SELECT. The top of the tree says SELECT. It also empties your orders table.

There are more like it. One quietly copies a table somewhere else. One takes locks on rows it was only supposed to read. All of them look like reads at the top and are not reads underneath.

That is the whole lesson: you cannot check the top of the tree. You have to walk all of it, every branch, and know what each thing means. And when you meet something the parser does not understand, you refuse it, because unknown is not the same as safe.

02Cheap to read is not the same as cheap to run

The next thing I built was a cost limit, because agents are enthusiastic and warehouses charge by the byte. On BigQuery you can ask what a query will cost without running it, which is free and exact, so the server checks that first and refuses anything over the ceiling. It also keeps a running total for the session, because the way an agent burns money is not one huge query. It is the same medium query two hundred times.

Then a query slipped through that passed every byte check. It reads fifteen megabytes. It joins a table to itself in a way that matches everything to everything, and it produces fourteen billion rows.

Bytes read tells you how much you looked at. It says nothing about how much work you are about to do. So there are two limits now.

03The model does not get to say who it is

This one is short and I feel strongly about it. No tool takes a user name as an input. Not one. There is even a test that fails if anyone ever adds one.

An agent that can tell you who it is has told you nothing. Identity comes from configuration, from outside the conversation, always.

Row level rules get pushed into the query itself, into the tree, so each protected table is quietly replaced with a filtered version of itself. Gluing a WHERE clause onto the end would have been easier and it would have lasted right up until the first query that ended in OR 1=1.

04Say no in a way the model can use

A refusal that just says "denied" is a dead end. The agent tries again, slightly differently, forever.

So every refusal comes back with the reason, the limit it crossed, by how much, and a suggestion built from the query itself. Results come back capped, and when they are cut short the answer says so out loud instead of pretending that was all the data. To get more you use a cursor the server hands you, which the model cannot forge. It can ask for more of that. It never gets to quietly change what "that" was.

My favourite tool is the free one. It checks a query and prices it without running it. Given a free way to ask "would this be allowed and what would it cost", the model actually uses it, and its expensive mistakes turn into cheap refusals it can learn from. Without it, the only way to find out a query was too expensive is to be billed for it.

Last piece: everything gets written down, including the refusals, and every call has to say why it is being made. A warehouse log tells you a service account read four terabytes. This tells you an agent read them because it was chasing a refund that did not add up. Only one of those is worth anything to the person reading it later.

05What I took away

The interesting result was not that my version scored well. It was that the sensible looking approach, the one most people would ship, still misses a quarter of the attacks. Parsing the query is not the same as understanding it.

And a guard is only useful if it almost never blocks real work. A tool that cries wolf gets switched off in a week, and then you have no guard at all.
