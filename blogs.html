I hadn't written a Kubernetes operator, so I wrote one for vLLM

A job I wanted asked for Kubernetes operator experience and for debugging hardware issues. I had neither on paper. So I wrote a small vLLM operator — a CRD that takes a model, a tensor-parallel size and a GPU memory fraction, and reconciles it into serving pods — and then spent most of my time not on the happy path, but on the three reconciliation problems nobody writes about.

Draft — 2 of 4 experiments complete. Finished: admission and probes. Still running on my cluster: rollout and gpu-health. Those sections are marked inline; the prose around them is final.

00Read this before you trust any number

I don't have a GPU. Everything on the Kubernetes side of this is real: a real three-node cluster, the real scheduler, real kubelet probes, real EndpointSlice propagation, a real operator process reconciling real nvidia.com/gpu extended resources that the scheduler enforces. What is not real is the engine. sim/fakevllm.py is a simulator that reproduces vLLM's startup phases and its memory arithmetic — weights, CUDA context, the profile run, the KV cache carve-out, CUDA graph capture — with per-phase timings scaled from published A10 numbers.

So the control-loop behaviour transfers and the throughput numbers do not exist. I have deliberately not reported a single token/sec figure. Twice during this build the simulator was wrong in a way that changed a result, and both times the bug turned out to be the interesting part.

01The readiness probe question has two answers pulling in opposite directions

vLLM allocates its KV cache at startup, after loading weights. Between process start and "can serve a request" there are minutes. That single fact breaks readiness probes in two directions at once, and which one bites you depends on how you deploy.

Direction one: the probe is too strict, and kills a healthy pod

Stock vllm serve does not open its HTTP port until the engine is up. A liveness probe with Kubernetes' default budget — periodSeconds: 10, failureThreshold: 3 — gives the pod 30 seconds. An 8B model takes about 115. The kubelet kills it, the container restarts, it gets killed again. CrashLoopBackOff, forever, on a pod whose only problem is that it was told to load a large model. This is the most common vLLM-on-Kubernetes bug and it is entirely self-inflicted.

Direction two: the probe is too permissive, and routes traffic into a pod that can't serve

Put vLLM behind a proxy, or run it with a multi-process API server, and the port answers immediately. A tcpSocket probe passes at t ≈ 0. The pod joins the Service. Requests arrive at an engine with no KV cache.

Same model, same load, four probe contracts in the stock topology. Served counts the whole 220 s window including the ~117 s cold start, during which every strategy is correctly unavailable:

In this topology every contract except naive looks identical, and that is the point: the column that separates them is misrouted, and it only lights up in the proxied topology, where the port answers before the engine does. /health behaves exactly like tcpSocket there, because "the HTTP server is up" and "the engine has capacity" are different questions and only one of them is being asked. Those runs are still going; I'm not going to quote a number I haven't measured.

The contract that works is kvGate, and the interesting part is that it is not a probe at all. A startupProbe with a large failureThreshold absorbs the weight load — liveness is not armed until startup succeeds, Kubernetes guarantees that ordering, and it is the entire fix for direction one. Readiness hits /ready. And then a pod readiness gate lets the operator, not the kubelet, hold the final vote:

spec:
  readinessGates:
    - conditionType: serving.vllmops.io/kv-cache-ready

The operator scrapes /metrics on the pod IP, looks for vllm:num_gpu_blocks > 0, and patches that condition. Until it does, the pod stays out of Service endpoints no matter how cheerful the kubelet is. Readiness gates are an obscure corner of the pod API and they are exactly right here, because "does this engine have a KV cache" is a question only something holding a model of vLLM can answer.

02What I got wrong, twice

The port was open the whole time

My first probe results were nonsense — tcpSocket passing instantly in a topology where the port was supposed to be shut. ThreadingHTTPServer(...) binds and listens in its constructor; I was delaying only serve_forever(). So the socket was accepting connections into the backlog for the entire weight load while nothing answered them.

My simulator bug is also a real deployment bug: a TCP probe against a listening socket with no accept loop passes happily. That is one more reason tcpSocket is the wrong probe for this workload.

The pod that would not die

My naive arm did not CrashLoopBackOff the way I predicted. It was killed at ~32 s and did not actually terminate until ~152 s — and in between it finished loading, served traffic for thirty seconds, then vanished mid-request.

Linux applies no default signal disposition to PID 1, so a Python process running as PID 1 with no SIGTERM handler simply ignores it. Every kubelet-ordered kill then stalls for the full terminationGracePeriodSeconds. Measured directly: 1 s to stop with a handler, the entire timeout without one. That interacts badly with this workload specifically, because vLLM needs a long grace period to drain in-flight decodes — the longer you make it for good reasons, the longer a condemned pod lingers.

03Rolling out when the replacement needs a GPU you don't have

A Deployment's rolling update assumes pods are cheap and interchangeable. A vLLM pod is neither: it takes minutes to become useful and it holds a GPU that its own replacement also needs. With one GPU and maxSurge: 1, the surge pod is unschedulable — it is waiting for a device held by the pod it is meant to replace. The rollout does not fail. It just never finishes.

So the operator reads real spare capacity and picks a strategy. When a GPU is free it surges: build the replacement, wait for its KV cache, then retire the incumbent — zero downtime, one GPU of headroom for the duration. When nothing is free it drains first: flip the pod's serving label so EndpointSlice propagation pulls it out of rotation, poll vllm:num_requests_running until in-flight decodes finish, then delete and rebuild.

Drain-first does not avoid the downtime; nothing can, because the replacement cannot start until the GPU is released. What it buys is that the rollout completes and no request is cut mid-stream.

There is a bug here I shipped and then found. My first spare-GPU calculation was allocatable-minus-allocated, which is the obvious definition and wrong: a node can be Ready and still refuse the surge pod because it is cordoned, NotReady, or carrying a NoSchedule taint. Counting those as spare made the operator choose Surge and then deadlock waiting for a pod the scheduler would never place — reproducing the exact Deployment failure it exists to prevent.

04How does an operator know a GPU is sick?

This is the one I most wanted to answer. Kubernetes has no concept of a degraded GPU. The device plugin advertises nvidia.com/gpu: 1 because the device enumerates, not because it works. A GPU that throws Xid 79 and falls off the bus is still counted, so the scheduler keeps placing pods there and the pods keep dying, with no signal anywhere in the Kubernetes API.

A DaemonSet tails the kernel log for NVRM: Xid lines and translates node-fault ones into a node condition plus a NoSchedule taint. The operator watches for that, evicts its pods, and excludes the node from nodeAffinity. The classification is the whole job — an agent that cordons on any Xid is worse than no agent:

classxidswhat it meansnode action
APP13, 31, 43, 45illegal instruction, out-of-bounds access — the workload misbehavednone
FATAL48, 64, 74, 79, 95, 119uncorrectable ECC, NVLink failure, GPU off the buscordon now
DEGRADE63, 92, 94ECC page retirement, rising single-bit ratecordon past a threshold
UNKNOWNanything else—none, and say so

Xid 13 and 31 are the most common Xids in an inference fleet and they are overwhelmingly the application's fault. Cordoning on those means one user's malformed request drains healthy capacity across your cluster. Being wrong in the permissive direction costs one pod restart; being wrong in the aggressive direction costs a node. So UNKNOWN fails toward keeping the node in service.

05The part I didn't plan: don't schedule pods you can prove will fail

Everything vLLM discovers during its profile run is a pure function of the model architecture, tensor-parallel-size, max-num-seqs, max-model-len, gpu-memory-utilization and total GPU memory. None of it requires a GPU to compute. So the operator runs vLLM's own arithmetic at admission and refuses to create a pod that cannot allocate a KV cache.

Across 24 of 24 configurations, exact KV-block agreement. predict() costs 1.24 µs; the engine needs 102.7–270.1 s to reach the same verdict. That is the whole argument for admission control: the same answer, eight orders of magnitude cheaper, delivered as a status condition instead of a CrashLoopBackOff.

It also surfaced something I did not expect. There is a window of gpu-memory-utilization that boots, bounded below by "no memory left for the KV cache" and above by "no headroom left for CUDA graph capture" — and raising max-num-seqs narrows it from both ends, because the profile run's peak activation grows and so does the graph pool:

06What I'd fix next

  • Calibrate the predictor against real hardware. Its structure is right; its constants — CUDA context size, fragmentation headroom, activation scaling — are estimates. On a real A10 I'd fit them against nvidia-smi and vLLM's own logged block count, and treat a prediction/actual mismatch as a reportable operator error rather than silently trusting the model.
  • Quarantine needs a way back. A cordoned node stays cordoned until something clears the condition. Real recovery means a GPU reset, a re-check of ECC retired-page counts, and an un-taint — with hysteresis, so a flapping device doesn't oscillate.
  • Drain-first should pre-warm. Nothing stops the operator pre-pulling the image and warming the weights into page cache on the target node before it releases the GPU. That should cut a meaningful slice off the downtime, and it's the highest-value thing left.
  • Multi-node tensor parallelism is unhandled. tp > 8 means gang-scheduling across nodes, and every decision above gets harder when a "replica" is a set of pods that must live or die together.
  • No PodDisruptionBudget, no leader election. Two operator replicas would fight. A single replica is a cop-out I'd rather fix than document.

07Run it

Everything here is reproducible on a laptop — no GPU required, because the engine is simulated and the cluster is not:

make up            # kind cluster + images + operator
make experiments   # exp0..exp3, writes results/*.json
make figures       # regenerate the SVGs from results
